# Kiosk Backend — API Routes

Complete route reference for the NestJS backend in this repository. Generated by
reading the controllers, Zod DTOs, services, and Prisma schema. Intended for
AI agents and humans integrating with the API.

## Quick facts

| Item | Value |
| --- | --- |
| Base URL | `http://localhost:${PORT ?? 3000}` (no global prefix, no `/api`, no version segment) |
| Framework | NestJS 12, Express adapter, ESM |
| Database | PostgreSQL via Prisma 6 (`prisma/schema.prisma`, `DATABASE_URL` in `.env`) |
| Content type | `application/json` for request bodies |
| Auth | `POST /auth/login` validates email + password, creates a server-side session and sets an HTTP-only `kiosk_session` cookie. `POST /auth/register` creates the account and the session in one request. `AuthGuard` resolves the cookie on every request; guests may only use `@Public()` routes. |
| Abuse protection | Global per-IP rate limiting (`@nestjs/throttler`, 600/min default) with tighter limits on login (10/min), signup (5/hour), image upload (30/hour) and the view beacon (60/min); `helmet` adds security headers |
| Signup notice | A successful registration POSTs to `SIGNUP_WEBHOOK_URL` (Slack/Discord/any), fire-and-forget |
| Validation | Global `StandardSchemaValidationPipe`; Zod schemas attached per body with `@Body({ schema })` |
| Transform | Validation pipes transform input (`.trim()`, email `.toLowerCase()`), so stored/returned values are transformed |
| Pagination / filtering | **None.** `GET /<resource>` returns every row, ordered by `id` ascending |
| Audit actor | Derived from the session (`createdBy` / `updatedBy`); the client cannot choose it |
| Timestamps | `createdAt` / `updatedAt` are ISO 8601 strings, maintained by Prisma |

## Security model

- **Session cookie**: `POST /auth/login` creates a `Session` row keyed by the
  SHA-256 of a random token and sets `kiosk_session` (`HttpOnly`, `Secure` in
  production, `SameSite` from `SESSION_COOKIE_SAMESITE`: `none` by default in
  production for the cross-origin static frontend, `lax` in local dev).
- **Global guard**: every route requires a session unless it is decorated with
  `@Public()`. `@Roles('ADMIN')` protects catalog writes (users admin actions,
  categories, descriptions, facet schemas/options).
- **Public routes**: `GET /`, `/healthz`, `/auth/login`, `/auth/me`, `/auth/register`,
  `/listings` (active rows), `/listing-translations`, `/listing-images`
  (including `/file`), `/categories`, `/descriptions`, `/languages`, `/regions`,
  `/facet-schemas`, `/facet-value-options`, `/facet-value-selections`,
  `/suggest`, `POST /users` (registration; role forced to `USER`), and
  `POST /listings/:id/view` (the statistics beacon).
- **Rate limiting and headers**: `ThrottlerGuard` runs before the session lookup
  (in-memory store, per IP; `trust proxy` is enabled so Render's forwarded IP is
  used). `helmet` sets the usual security headers with
  `Cross-Origin-Resource-Policy: cross-origin` so listing images stay embeddable,
  and without a CSP (the SSR server owns the page CSP).
- **Signup/session policy**: `POST /auth/register` creates `USER` rows only and
  signs the account in. `POST /auth/login` answers `401` for social-only accounts
  (no password hash) as well as for wrong passwords, so it never reveals which
  emails exist.
- **Google sign-in** (`GET /auth/google` → `GET /auth/google/callback`): a
  server-side authorization-code flow with a `state` cookie (10 min, scoped to
  `/auth/google`); the client secret never reaches the browser. Accounts are
  matched by the provider's stable `sub` first, then by email:
  - an existing **link** signs in (even if the Google email changed);
  - an email that already has a **password account** is **refused**
    (`/login?error=email_in_use`) — our signup emails are unverified, so silent
    linking could hand someone else's account to the mailbox owner;
  - an email owned by a provider-only account is linked (both sides verified);
  - otherwise a `USER` is created (no password hash) and linked.
  Inactive accounts, unverified Google emails and provider errors also redirect
  to `/login?error=<code>`; `from` is limited to local paths.
- **Admin bootstrap**: on boot, `ADMIN_EMAIL` promotes that account to `ADMIN`
  (creating it when `ADMIN_PASSWORD` is set). Signup always creates `USER` rows,
  so this is how the first admin exists on a fresh deployment.
- **Ownership**: listing writes, translations, images and facet selections are
  limited to the listing owner (admins bypass). Drafts are only visible to their
  owner and return `404` to everyone else.
- **Chat privacy**: threads, messages, inbox rows and listing links are limited
  to participants (thread creator, listing owner, or inbox user). `chat-messages`
  and `chat-events` ignore any client-provided `userId`; the SSE stream forwards
  only events for the caller's threads.
- **CSRF**: cookie-authenticated writes also require an allowed `Origin`; CORS
  is restricted to `FRONTEND_ORIGINS` and `credentials: true`.
- **Environment**: `SESSION_COOKIE_NAME`, `SESSION_TTL_DAYS` (7 by default),
  `SESSION_COOKIE_SAMESITE` (`none`/`lax`/`strict`), `FRONTEND_ORIGINS`,
  `SIGNUP_WEBHOOK_URL`, `PUBLIC_ORIGIN`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`,
  `ADMIN_NAME`, `VISITOR_COOKIE_NAME`, `GOOGLE_CLIENT_ID`,
  `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`.

## Conventions

### Path parameters
- `:id` is parsed with `ParseIntPipe` (base-10 integer). `/users/abc` and
  `/users/1.5` return `400`.

### Update bodies
- Every `Update*Dto` is `createSchema.partial()` plus a refinement requiring at
  least one key. `{}` returns `400` with message `At least one field must be provided`.
- On `PATCH`, only supplied fields change; omitted fields keep their value.

### Validation errors (`400`)
Zod issues are flattened into a string array:

```json
{
  "message": ["email: Email must be a valid email address"],
  "error": "Bad Request",
  "statusCode": 400
}
```

### Error mapping
| Situation | Status | Body message |
| --- | --- | --- |
| Unknown `:id` on `GET`/`PATCH`/`DELETE` | `404` | `<Model> <id> not found` (find) / `<Model> not found` (update/delete) |
| Duplicate unique value (`P2002`) | `409` | `A <model> with the same unique value already exists` (users: `A user with this email already exists`) |
| Missing related row (`P2003`) | `400` | `A related record for this <model> does not exist` |
| Delete a row still referenced by a required relation | `400` | `A related record for this <model> does not exist` (Prisma `P2003`) |
| Invalid body / empty update | `400` | Zod issue list |
| Non-integer `:id` | `400` | ParseIntPipe message |

### Audit columns
- Every entity except `User` has `createdAt`, `updatedAt`, `createdBy`, `updatedBy`.
- The actor comes from the **session cookie** (`@ActorId()` reads `request.user`);
  the client cannot choose it. Guest writes never reach a handler because every
  write route requires a session.
- `createdBy` / `updatedBy` are plain integers, **not** foreign keys, so audit
  data survives user deletion.
- `x-actor-id` is no longer read; an old client sending it has no effect.

## Resource schemas

Field type notation: `int` = positive JSON integer, `string`, `enum`, `boolean`,
`string | null`. All `id` and foreign-key fields are integers.

### `/users` — User
Source: `src/users/users.controller.ts`, `src/users/users.service.ts`

Create body (`CreateUserDto`):

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `name` | string | yes | trimmed, 1–100 chars |
| `email` | string | yes | trimmed, lowercased, valid email, max 254, **unique** |
| `password` | string | yes | 8–200 chars; stored as scrypt hash |
| `role` | enum | no | `"USER"` (default) or `"ADMIN"` |
| `isActive` | boolean | no | default `true` |

Update body (`UpdateUserDto`): any subset of the above, at least one field.
`password` is re-hashed when present.

Response fields: `id`, `name`, `email`, `role`, `isActive`, `createdAt`,
`updatedAt`. **`passwordHash` is never returned. No audit columns.**

`passwordHash` is null for accounts created through Google (they sign in there);
the column is otherwise the scrypt hash. Terms acceptance is stored in
`acceptedTermsAt` (set by `/auth/register` and by the first Google sign-in).

`OAuthAccount` (one row per provider identity) holds `provider` (`google`),
`providerAccountId` (Google `sub`), `email` and `userId`; it is unique on
`(provider, providerAccountId)` and `(provider, userId)` and cascades with the
user.

Notes:
- `POST /users` with a duplicate `email` → `409`.
- Users can be deleted even if listings reference `userId` (that column is not a FK).

### `/listings` — Listing
Source: `src/listings/listings.controller.ts`, `src/listings/listings.service.ts`

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `categoryId` | int | yes | FK → `categories.id` (must exist) |
| `regionId` | int | no | FK → `regions.id`; defaults to `0`, the "All regions" row |
| `orientation` | enum | yes | `"buy"` or `"sell"` |
| `userId` | int | yes | plain integer (not a FK), semantically a user id |
| `isActive` | boolean | no | defaults to `true`; the wizard creates drafts with `false` and Publish sets `true` |
| `price` | number \| null | no | nullable float, the answer to the price question |
| `year` | int \| null | no | nullable integer, the answer to the year question |

Response: `id`, `categoryId`, `regionId`, `orientation`, `userId`, `isActive`,
`price`, `year`, `createdAt`, `updatedAt`, `createdBy`, `updatedBy`,
`facetsCount`.

`facetsCount` is the number of answered interview questions: the listing's
`FacetValueSelection` rows plus `1` for orientation and `1` when `price` is not
null and `1` when `year` is not null. Brand-new listings therefore start at `1`
(orientation is required).

### `/listings/:id/view` and `/listings/:id/stats` — ListingEvent
Source: `src/listing-events/listing-events.controller.ts`,
`src/listing-events/listing-events.service.ts`

`POST /listings/:id/view` is the public beacon fired by the listing page. The
body is optional (`{ "source": "search", "language": "hr" }`, both validated).
It answers `204` and never throws for an ignored request.

Ignored requests:

- known crawlers, link-preview bots, Lighthouse, uptime monitors (`User-Agent`);
- `Sec-Purpose` / `Purpose` / `X-Purpose` containing
  `prefetch`, `prerender` or `preview`;
- unknown or unpublished (draft) listings;
- the listing owner's own visit (session user id equals `Listing.userId`).

One row is written per `(listingId, type, visitorId, day)`: the unique index
makes a refresh, a second tab or React's double effect in development a no-op.
`day` is a `DATE` (UTC midnight). The visitor id is a random 128-bit value kept
in the `kiosk_visitor` cookie (`HttpOnly`, one year, `SameSite=None; Secure` in
production, `Lax` locally) — the API never stores IPs, user agents or session
tokens with the event. `VISITOR_COOKIE_NAME` overrides the cookie name.

`GET /listings/:id/stats?days=14` (owner or admin) returns:

```json
{
  "listingId": 25,
  "days": [{ "date": "2026-11-18", "views": 1 }],
  "totals": { "views": 1, "viewsInWindow": 1, "contacts": 1 },
  "contactRate": 1
}
```

`days` is zero-filled and oldest-first (`days` is clamped to 1–90, default 14),
`totals.views` is all-time, `contacts` counts `listing-chat-threads` rows and
`contactRate` is `contacts / views` (0 without views). Deletes the listing's
events when the listing is deleted (`onDelete: Cascade`).

### `/listing-translations` — ListingTranslation
Source: `src/listing-translations/listing-translations.controller.ts`,
`src/listing-translations/listing-translations.service.ts`

One localized title per listing and language, keyed by `(listingId, language)`.
Titles are deliberately separate from the shared `Description` catalog: deleting
a listing cascades its titles, and the rows have a real FK to `listings.id`.

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `listingId` | int | yes | FK → `listings.id` |
| `language` | string | yes | FK → `languages.code` (`en`, `hr`) |
| `title` | string | yes | trimmed, 1–225 chars |

`POST` upserts: the same call creates a missing translation or replaces the
existing one. `DELETE` removes one language. Clients resolve missing
translations themselves; the frontend falls back to the UI language, English,
any available title, then the generated `"Category #id"` label.

### `/categories` — Category
Source: `src/categories/categories.controller.ts`, `src/categories/categories.service.ts`

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `descriptionId` | int | yes | references `descriptions.id`; existence checked by the API |
| `parentCategoryId` | int \| null | no | FK → `categories.id`; `null`/omitted = root category |

Response: `id`, `descriptionId`, `parentCategoryId`, `createdAt`, `updatedAt`,
`createdBy`, `updatedBy`, `facetsCountMax`, `facetsCountMaxAnswerable`.

`facetsCountMax` is the number of interview questions that apply to the
category: every generic option `FacetSchema`, every option `FacetSchema` defined
on the category or one of its ancestors, plus the two numeric range questions
(`price` and `year`). Orientation and the range questions are always counted,
even when an older database has no facet rows for them, so the total is at least
`3`.

`facetsCountMaxAnswerable` counts only the option facets and excludes the
numeric price/year questions. Orientation is included even though its value is
read from `Listing.orientation` instead of a `FacetValueSelection`. In the
current catalog the four shared questions are orientation, condition, price and
year, so the virtual all category reports `4` and `2`.

`GET /categories` also returns a virtual **all** category with `id: 0`,
`descriptionId: 0`, no audit values, and the generic questions shared by every
category. It has no row in the database and cannot be updated or deleted. `GET
/categories/0` returns the same object.

Notes: deleting a category with child categories sets their `parentCategoryId`
to `null` (`SetNull`); deleting one still referenced by a listing or facet schema
returns `400`.

### `/regions` — Region
Source: `src/regions/regions.controller.ts`, `src/regions/regions.service.ts`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | int | `0` is the global "All regions" row |
| `code` | string | ISO 3166-1 alpha-2, or `ALL` for id `0` |
| `descriptionId` | int | name in each language, stored like category descriptions |

The table is seeded by the `add_regions` migration with the EU member states and
the ex-Yugoslav countries outside the EU (Bosnia and Herzegovina, Serbia,
Montenegro). Listings carry `regionId`; `0` means the listing has no specific
region (existing rows and listings created while "All regions" is selected).

`GET /regions/detect` reads the visitor's address from `x-forwarded-for`
(`x-real-ip` and `cf-connecting-ip` are also accepted) and maps its ISO country
code to a region. Private addresses, unknown countries and failed geo lookups
return `{ "regionId": 0, "countryCode": null }`. The geo provider is
`api.country.is` by default; `GEO_LOOKUP_URL` overrides it and may contain
`{ip}`. The response can be a bare country code or JSON with `country`,
`country_code` or `countryCode`. Results are cached in memory for six hours; IP
addresses are never stored.

### `/descriptions` — Description
Source: `src/descriptions/descriptions.controller.ts`, `src/descriptions/descriptions.service.ts`

A description is stored as one row per language under a shared `id`
(`@@id([id, language])`). The API returns one object per id with a
`translations` map, and every configured language must be supplied on create.

`name` marks an interface string: it holds the key the React app uses
(`common.close`) and is stored on every language row. Category and facet
descriptions omit `name`, so their `name` is `null`. A name is unique per
language; creating or renaming onto an existing name returns `409`.

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `name` | string \| null | no | dotted i18n key, 1–100 chars, unique per language; omitted for category/facet text |
| `translations` | object | yes (create) | map of language code → text; trimmed, 1–225 chars each |

`POST /descriptions` requires a text for **every** language in the `Language`
table (`en` and `hr`). A missing or unknown language returns `400`, for example
`Missing translations for: hr`.

```http
POST /descriptions
{ "name": "common.close", "translations": { "en": "Close", "hr": "Zatvori" } }
```

Category and facet descriptions are created without the name:

```http
POST /descriptions
{ "translations": { "en": "Cars", "hr": "Automobili" } }
```

`PATCH /descriptions/:id` accepts a subset of the map and updates only those
languages. A name can also be changed on its own; it is written to every
language row:

```http
PATCH /descriptions/7
{ "translations": { "hr": "Vozila" } }
```

```http
PATCH /descriptions/7
{ "name": "facet.vehicleType" }
```

Response: `id`, `name`, `translations` (`{ "en": "...", "hr": "..." }`),
`createdAt`, `updatedAt`, `createdBy`, `updatedBy`. `createdAt`/`createdBy` come
from the oldest translation row; `updatedAt`/`updatedBy` from the most recently
changed one.

Notes: deleting a description referenced by a category, facet schema, or facet
value option returns `400`. Category/FacetSchema/FacetValueOption reference
`descriptions.id` but cannot declare a foreign key (the API checks existence on
create/update), because `id` is no longer unique on its own.

Read-only: the migration seeds `en` (English) and `hr` (Hrvatski). Adding a

### `/suggest` — facet autocomplete
Source: `src/suggestions/suggestions.controller.ts`,
`src/suggestions/suggestions.service.ts`

Powers the structured chip search input. Suggestions are facet values, not ad
free text, and counts are computed from `FacetValueSelection` rows.

| Query | Type | Required | Notes |
| --- | --- | --- | --- |
| `q` | string | no | Matched against translated value labels, facet labels and facet names |
| `lang` | string | no | `en` (default) or `hr`; unknown codes fall back to English text |
| `category` | int | no | Selected category id; includes generic facets and facets inherited from ancestor categories. Omitted = all categories |
| `orientation` | `buy` \| `sell` | no | Optional legacy filter; orientation chips are preferred |
| `chips` | JSON string | no | `[{"kind":"value","facet":"condition","valueId":"1"}]` (orientation chips use `valueId` `buy`/`sell`) |

Response:

```json
{
  "suggestions": [
    {
      "facet": "condition",
      "facetLabel": "Condition",
      "valueId": "1",
      "label": "New",
      "count": 1
    }
  ]
}
```

Only values with `count > 0` are returned, up to 60 rows, sorted by facet label,
then count descending, then value label. Chips are AND constraints. A facet that
already has a value chip is omitted from the response (the data model allows one
value per facet per listing), so the client cannot build an impossible query.
When `category` is set, a facet is included if it is marked `isGeneric` or is
defined on the selected category or one of its ancestors. This is how a parent
category's facets (for example Electronics/brand) apply to its subcategories.
`kind: "range"` chips are accepted for forward compatibility but ignored until
numeric facets exist. An orientation value chip
(`{"kind":"value","facet":"orientation","valueId":"sell"}`) filters candidate
listings by `Listing.orientation`. The frontend calls this as `/api/suggest`
through the Vite proxy.

```bash
curl 'http://localhost:3000/suggest?q=new&lang=en&category=2'
curl 'http://localhost:3000/suggest?q=&lang=hr&category=6&chips=%5B%7B%22kind%22%3A%22value%22%2C%22facet%22%3A%22frame_size%22%2C%22valueId%22%3A%228%22%7D%5D'
```

### `/chat-events/stream` — live chat stream
Source: `src/chat-events/chat-events.controller.ts`,

### `/listing-images` — ListingImage
Source: `src/listing-images/listing-images.controller.ts`,
`src/listing-images/listing-images.service.ts`

A listing can have zero or more images. Every upload is re-encoded to WebP
(max 1600 px on the longest side, quality 82, EXIF rotation applied) and the
bytes are stored in PostgreSQL in the `ListingImageData` table, keyed by the
`ListingImage` row. Keeping the bytes in a separate table means metadata and
listing queries never load them, and they survive redeploys. The original upload
file name is **not** stored — `fileName` is a generated logical UUID name.

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `file` | file | yes | multipart field; JPEG, PNG, WebP, GIF or AVIF; max 10 MB |
| `listingId` | int | yes | FK → `listings.id`; sent as a multipart text field |

Response: `id`, `listingId`, `mimeType`, `size`, `primaryImage`, `url`,
`createdAt`, `updatedAt`, `createdBy`, `updatedBy`. `url` is API-relative
(`/listing-images/<id>/file`); with the frontend's Vite proxy it becomes
`/api/listing-images/<id>/file`.

The first image uploaded for a listing becomes its primary image
(`primaryImage: true`) automatically. `PATCH /listing-images/:id` with
`{ "primaryImage": true }` promotes that image and clears the flag on its
siblings, so a listing has at most one primary image. Lists are returned with
the primary image first. Deleting a listing cascades its image rows, and
`ListingImageData` cascades with them.

```bash
curl -X POST http://localhost:3000/listing-images \
  -b session-cookies.txt \
  -F 'listingId=25' \
  -F 'file=@photo.jpg;type=image/jpeg'
```

### `/facet-schemas` — FacetSchema
Source: `src/facet-schemas/facet-schemas.controller.ts`, `src/facet-schemas/facet-schemas.service.ts`

A facet is one interview question and one filter. `type` decides how it is
answered: `option` facets offer `FacetValueOption` values and are stored as
`FacetValueSelection` rows; `numeric` facets are range questions stored in
dedicated `Listing` fields (price and year). `required: true` facets must be
answered before a listing can be published.

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `descriptionId` | int | yes | references `descriptions.id`; existence checked by the API |
| `name` | string | yes | trimmed, 1-225 chars, **unique** |
| `categoryId` | int | yes | FK → `categories.id` |
| `isGeneric` | boolean | no | default `false`; generic facets apply to products in every category (the ALL PRODUCTS section) |
| `type` | enum | no | `"option"` (default) or `"numeric"` |
| `required` | boolean | no | default `false`; required questions gate publishing |

Response: `id`, `descriptionId`, `name`, `categoryId`, `isGeneric`, `type`,
`required`, `createdAt`, `updatedAt`, `createdBy`, `updatedBy`. Deleting a
schema cascades to its options.

The catalog migration marks `condition` as required and generic, adds generic
facets for orientation (`name: "orientation"`, type `option`, required, options
For Sale / Wanted), price and year (type `numeric`), moves `brand` to
Electronics and adds the Mobile phones `screen_size` facet. Orientation is a
facet in the API and UI but is persisted on `Listing.orientation`; price and year
are persisted on `Listing.price` and `Listing.year`. The frontend always renders
these four questions first (orientation, condition, price, year), even if an
older database has no rows for them.

## Relationships, uniqueness, and creation order

### Foreign keys

| Child | Field | Parent | onDelete |
| --- | --- | --- | --- |
| Listing | `categoryId` | Category.id | Restrict (default) → `400` |
| Category | `parentCategoryId` | Category.id | Set Null |
| ChatMessage | `threadId` | ChatThread.id | Cascade |
| ListingChatThread | `listingId` | Listing.id | Cascade |
| ListingChatThread | `chatThreadId` | ChatThread.id | Cascade (unique) |
| InboxItem | `chatThreadId` | ChatThread.id | Cascade (unique) |
| ListingImage | `listingId` | Listing.id | Cascade |
| FacetSchema | `categoryId` | Category.id | Restrict → `400` |
| FacetValueOption | `schemaId` | FacetSchema.id | Cascade |
| FacetValueSelection | `facetValueOptionId` | FacetValueOption.id | Cascade |
| FacetValueSelection | `listingId` | Listing.id | Cascade |

Plain integer columns with **no** foreign key: `Listing.userId`,
`InboxItem.userId`, `Category.descriptionId`, `FacetSchema.descriptionId`,
`FacetValueOption.descriptionId`, `createdBy`, `updatedBy`.

### Unique constraints
- `users.email`
- `languages.code` (primary key)
- `descriptions` composite primary key `(id, language)`
- `descriptions (name, language)` for named interface strings; rows with a null name are unaffected
- `facet-schemas.name`
- `listing-chat-threads.chatThreadId`
- `inbox-items.chatThreadId`
- `listing-images.fileName`

### Safe creation order
1. `POST /users`
2. `POST /descriptions`
3. `POST /categories` (uses a description; `parentCategoryId` optional)
4. `POST /facet-schemas` (description + category)
5. `POST /facet-value-options` (description + facet schema)
6. `POST /listings` (category; `userId` is an integer)
7. `POST /chat-threads` (no body)
8. `POST /chat-messages` (chat thread)
9. `POST /inbox-items` (user id + chat thread)
10. `POST /listing-chat-threads` (listing + chat thread)
11. `POST /facet-value-selections` (facet value option + listing)

Delete in reverse order, or rely on cascade where it exists. Required relations
(no `onDelete`) block deletion with `400` while a child row exists.

## Examples

```bash
BASE=http://localhost:3000

# Root
curl $BASE/

# Create a description, then a category, then a facet schema
curl -X POST $BASE/descriptions \
  -H 'content-type: application/json' \
  -d '{"translations":{"en":"Cars","hr":"Automobili"}}'

curl -X POST $BASE/categories \
  -H 'content-type: application/json' \
  -b session-cookies.txt \
  -d '{"descriptionId":1}'

curl -X POST $BASE/facet-schemas \
  -H 'content-type: application/json' \
  -b session-cookies.txt \
  -d '{"descriptionId":1,"name":"color","categoryId":1}'

# Create a user (password is required, response never contains the hash)
curl -X POST $BASE/users \
  -H 'content-type: application/json' \
  -d '{"name":"Tino","email":"tino@example.com","password":"supersecret"}'

# Log in (valid credentials return the user id)
curl -X POST $BASE/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"tino@example.com","password":"supersecret"}'

# List everything (no pagination, ordered by id)
curl $BASE/users

# Update a subset of fields (empty body {} is a 400)
curl -X PATCH $BASE/users/1 \
  -H 'content-type: application/json' \
  -b session-cookies.txt \
  -d '{"isActive":false}'

# Delete
curl -X DELETE $BASE/categories/1 -i
```
